## 1. Task 1 — `launcher/raw_storage.py` and `launcher/virtual_exfat.py` internals

Round 3's UDPBD verdicts for the raw-device and virtual-exFAT modes rested on the two call sites in `udpbd_server/udpbd_server.py` (the gated capacity check at :208-209 and the validated raw seek). This round read both implementations in full (427 and 325 lines). **The round-3 verdicts stand**: the bounds the call sites rely on are really there —

- `RawDevice.seek` validates position and request end against capacity (`launcher/raw_storage.py:37-45`); `read` clamps to the request end and bounds its read-ahead cache to 64 KiB inside the request (:47-80); `write` does native-sector read-modify-write for unaligned spans, refuses past the request/capacity limit, and checks every native write's byte count (:82-108). The constructor refuses capacities that are not positive, 512-aligned and inside UDPBD's 32-bit sector count (:30-33). Exclusive mode unmounts longest-path-first, re-verifies mount state afterwards, and refuses boot/system targets (`open_raw_device` :301-330, `_exclusive_target` :333-343); `open_raw_device` also refuses writable-without-exclusive outright (:303-304).
- `VirtualExfat` is a frozen-inventory, read-only generated exFAT: the scan rejects symlinks/reparse points/special files, case-insensitive duplicate names, nesting past 64 and inventories past 100,000 entries (:138-160); `seek` is the capacity check round 3 credited (:228-233); payload reads re-`fstat` the file on every access and raise `ESTALE` if it changed since startup (:256-265); `write` always raises `EROFS` (:322-323). Layout arithmetic (bitmap self-sizing loop, FAT chain table, boot region + backup) was checked against the read path and is self-consistent.

One defect did surface in both classes, with the same shape — PS2SERVERS-066 below. It is **not reachable to wrong data through today's call sites** (every UDPBD request seeks first, and an `OSError` from seek aborts the request before any read/write), and the finding says so plainly; it is filed because both implementations of one interface share the trap and the interface is the launcher's public surface for these modes.

## 2. Task 2 — `compressed_iso/` wrappers, `router_status.py`, UDPFS send/window machinery

### 2a. compressed_iso (base 196, cso 152, zso 173, chd 334, chd_cuebin 567, limits 116)

The package has two postures. The **strict/inspection** posture (`strict=True`, used for metadata inspection of untrusted images) is exemplary: `limits.py` caps disc size, block size (`MAX_BLOCK = 16 MiB`, limits.py:13), index-table bytes and total decode budget, and `indexed_block` validates every offset span against the physical file before reading. The **serving** posture — the default, the one UDPFS reads games through — validates almost none of it: CSO/ZSO serving header parses check only `block_size != 0` (cso.py:76, zso.py:86), CHD's serving parse checks only `hunk_size != 0` (chd.py:280), and no serving path checks a block span for monotonicity or size. Three findings (063, 064, 065) come out of that gap, each with the in-repo correct model named (the strict path in the same package, `chd_cuebin.py`'s `MAX_HUNK_BYTES` cap at :28, or Go's `internal/compression`, which caps block at 16 MiB in `parseHeader`, image.go:255, and bounds every raw span in `decodeBlock`).

`chd_cuebin.py` itself is clean: the metadata chain walk is bounded in entries, bytes and tracks, detects cycles via a visited set, refuses offsets outside the file, and caps hunk bytes (chd_cuebin.py:28, :236-300); `layout()` validates every track's frame accounting before any byte is served. The Go mirror (`internal/compression/chd.go`) independently caps CHD hunks at the same 16 MiB (`maxCHDHunkBytes`).

### 2b. router_status.py (179 lines) — no finding

The parser is defensive on every axis: `is_status_query` requires the DISCOVERY type, the claimed service ID **and** the `PS2S` magic before anything answers (router_status.py:96-115); `parse_status_reply` refuses short packets, wrong type/service/magic and any version but its own, clamps an unrecognised state to `degraded`, and never reads the name past the packet (:144-179). This round also **executed the cross-language parity** the module's docstring promises: Python `build_status_reply(2, 0x19, 3, 3661, "router")` produced the 25-byte vector `0100f7f5…726f75746572`, and a Go test in the `/tmp` Edge copy asserted `protocol.StatusReply{StateBusy, 0x19, 3, 3661, "router"}.Marshal()` equals those bytes exactly, that `ParseStatusReply` round-trips them, and that `IsStatusQuery(MarshalStatusQuery())` holds — **all PASS (EXECUTED, both sides)**. Round-1 PS2SERVERS-012 (the protocol is answered three ways) is about duplication of the answering paths, not correctness; nothing here revises it.

### 2c. UDPFS send/window machinery (Python editions) — no new finding

Read as a subsystem this round (`udpfs_server/udpfs_server.py:122-176`, :2620-3044, Session :3199-3296; Core inherits all of it — its six overrides, round 3 §1b, touch none of these methods):

- Resent-request handling, DISCOVERY pre-emption of a transfer, and pushback to the session queue are all explicitly reasoned in comments and consistent between the two waits (:2778-2943).

The one wart in this machinery remains the one round 1 already filed — PS2SERVERS-020 (the 10× send-retry under the send lock, `_send_with_retry` :162-176, stacked under this window layer). It is not repeated here. ## 3. Task 3 — SMB2 SESSION_SETUP glue and `smb2_crypto.py`

### 3a. The glue (h_session_setup, smb2_server.py:822-927; dispatch/signing, :385-583)

Round 3 verified the auth and SPNEGO modules; the calling handler was only spot-read. Read in full this round, the glue is correct, including the one contract that decides whether a wrong password can become a guest logon:

- `Authenticator.verify` **raises `AuthError` on every failure** and returns `None` in exactly one case — open mode, where nothing was proved and there is no key (smb2_auth.py:277-324, contract stated at :283-291). The glue's branch is therefore sound: `base_key is None` → guest **only in open mode** (smb2_server.py:892-901); a bad password raises and `_dispatch` maps it to `STATUS_LOGON_FAILURE` (:636-640). Anonymous sessions are refused unless the authenticator is open (:879-888).
- The key lifecycle is right: challenge is per-connection and CSPRNG-fresh, cleared after use so a captured AUTHENTICATE cannot replay (:846-850, :908-910); the MIC is verified before the session is marked authenticated (:901-905); `signing_key` is installed only when a real session key exists (:911-913), derived per dialect by `smb2_crypto.signing_key`; LOGOFF deliberately keeps the key until its own reply has been packed and signed (:929-935).
- Verification is per-message, including per element of a compound (`_signature_check` over each `msg[offset:end]`, :446), with the spec's unsigned exemptions only for NEGOTIATE/SESSION_SETUP/CANCEL (:539-541) and unsigned-on-required refused (:551-570). Replies are signed per compound piece over header+body+padding (:483-493).

One residual: the CMAC dispatcher's fallback exists only at probe time — PS2SERVERS-067.

### 3b. smb2_crypto.py (452 lines) — structure/usage audit, no values printed

The native CMAC backends (bcrypt, OpenSSL 3 EVP_MAC, OpenSSL 1 CMAC_*) each **self-test once at probe time** against the pure implementation or the RFC 4493 empty-message vector and are discarded if they disagree (:218-340); `_native_cmac` caches the probe (:173-186). `verify` compares with `hmac.compare_digest` and length-guards first (:444-452). ## 5. New findings (PS2SERVERS-063…), sorted by benefit

## PS2SERVERS-063 / compressed_iso serving path trusts the file's declared block/hunk size — a 32-byte crafted CSO makes the server materialise a 256 MiB block; the strict path and Go both cap the same field at 16 MiB
- **Category:** 6 (Bug / security) / 4 (Memory)
- **Location(s):** `PS2-Servers/udpfs_server/compressed_iso/cso.py:70-80` (serving `_parse_header`: `uncompressed_size` and `block_size` taken from the header; the only check is `block_size == 0` at :76); same shape at `PS2-Servers/udpfs_server/compressed_iso/zso.py:83-87`; allocation at `cso.py:128` + the zero-padding at `cso.py:150` (`decompressed += b'\x00' * (block_size - len)`); block cache bounded by count only at `PS2-Servers/udpfs_server/compressed_iso/base.py:164-168` (32 blocks default). CHD twin (READ — no libchdr in this VM to execute): `PS2-Servers/udpfs_server/compressed_iso/chd.py:277-280,314` (`hunk_size` checked only for 0, then `ctypes.create_string_buffer(hunk_size)`). The caps that already exist in-repo: `limits.py:13` (`MAX_BLOCK = 16 MiB`, strict path only), `chd_cuebin.py:28` (`MAX_HUNK_BYTES = 16 MiB`), Go `internal/compression/image.go:255` and `chd.go` (`maxCHDHunkBytes`).
- **Problem:** EXECUTED at this pin: a crafted CSO file of **32 bytes total** whose header declares `block_size = 256 MiB` (one stored-raw block) made the *serving* wrapper's `read(1)` materialise a 268,435,456-byte block — measured peak-RSS delta **+256.0 MiB** — because the raw block is read short and then padded out to the declared block size. The same header through the strict path is refused (`InspectionLimit: Compressed disc/block size exceeds inspection limits`), and Go's `parseHeader` rejects the identical header (executed, §4). Real CSO block sizes are 2 KiB–32 KiB; nothing in the serving path enforces any ceiling, and the base cache's count-only bound (32 blocks) multiplies whatever a header declares (the exact trap Go's cache comment at image.go:28-36 describes avoiding with a byte budget). Game images are routinely downloaded from the internet, so "the operator chose the file" is a weak defence: a corrupt or hostile image is a memory-exhaustion of the server host, on exactly the low-RAM machines the Python editions target.
- **Fix:** Apply the package's own ceiling on the serving parse paths: refuse `block_size > MAX_BLOCK` (cso.py/zso.py) and `hunk_size > MAX_HUNK_BYTES` (chd.py) — the constants already exist in the same package; this is one comparison per parser, copied from the strict path, not a new limit regime.
- **Justification (addition):** Concrete, executed memory-exhaustion from a file-controlled field, with the bound, the constant and two working implementations (strict Python, Go) already in the repo.
- **Benefit:** Worst-case per-block allocation in the serving path drops from "whatever a header says" (GiB-scale) to 16 MiB; the count-bounded cache's worst case drops with it.
- **Effort:** S. **Risk:** Low (no conformant CSO/ZSO/CHD uses blocks or hunks above 16 MiB; the strict path and both cuebin readers already ship this ceiling). **Confidence:** High (READ + EXECUTED for CSO; READ for the ZSO/CHD twins)

## PS2SERVERS-064 / ZSO serving decompression retries LZ4 once per byte of an attacker-sized span — 100,000 decompress attempts for one 100 KB block — and can "succeed" with a zero-length block the base class then serves as data
- **Category:** 5 (Performance) / 6 (Correctness)
- **Location(s):** `PS2-Servers/udpfs_server/compressed_iso/zso.py:165-177` (the retry loop strips one trailing byte per failed attempt over the whole span); span size is whatever the offset table declares (`zso.py:131-158`, no bound — cf. 063); short/empty results pass straight through: unlike CSO, ZSO never pads a short block (contrast `cso.py:149-151`), and the length validation that would catch it exists only in strict mode (`base.py:155-161`). The bounded model is in the same package: `limits.py:82-92` (`indexed_block` tries at most `(1 << align) - 1` paddings, with the comment "Never retry once per byte of an attacker-controlled, potentially megabyte-sized span").
- **Problem:** EXECUTED at this pin: a crafted ZSO whose single block span is 100,000 bytes of garbage drove **exactly 100,000 `lz4.block.decompress` calls** for one block read (counted via a wrapping shim) — O(span²) byte-processing, ~5 GB of LZ4 scanning for a 100 KB block, on the session thread serving a console. Worse, the loop's terminal state is unsound: after 5,000 strippings of a zero-filled span the decompressor accepted a 1-byte remainder and `_decompress_block` returned a **zero-length block as success** (executed: `len = 0` against `block_size = 2048`). In non-strict mode nothing checks that length, and `base.read` advances `pos` by the *requested* `read_size` regardless of how much the block actually contained (base.py:91-96), so a short block silently becomes a short, position-shifted stream for the caller. The strict path's author already identified and fixed this exact loop shape in `indexed_block`; the serving path kept the original.
- **Fix:** Bound the serving retry the way `indexed_block` does — at most `(1 << align) - 1` trailing-byte attempts (alignment padding is the loop's only legitimate purpose) — and treat a decoded block shorter than the expected non-final length as the error strict mode already makes it, or pad it as CSO does. Both changes copy code that exists in this package.
- **Benefit:** Per-block decompression cost becomes linear and bounded; a class of silent short/garbled reads from damaged ZSOs becomes a visible error.
- **Effort:** S. **Risk:** Low (legitimate ZSO blocks need at most `align` padding retries; that is the strict path's shipped assumption). **Confidence:** High (READ + EXECUTED)

## PS2SERVERS-065 / CSO serving never validates a block's span: an index pair one entry apart makes it read the rest of the file as one block's input
- **Category:** 6 (Bug — robustness) / 4 (Memory)
- **Location(s):** `PS2-Servers/udpfs_server/compressed_iso/cso.py:106-128` (`read_size = next_offset - offset` at :124, used unchecked at :128); Go's model: `internal/compression/image.go:437-447` (span rejected when `end < start` or `end - start > 2×block + 4096`, before any read). Strict Python likewise validates spans against the physical file (limits.py:64-77).
- **Problem:** EXECUTED at this pin, two cases. (a) A CSO whose second index entry is exactly one less than the first (align 0) yields `read_size == -1`, and `file.read(-1)` is Python's read-to-EOF: the recorded read call was `(-1, 4194304)` — the wrapper consumed the file's entire 4 MiB tail as a single block's compressed input and accepted the block. Input allocation per block is therefore "the rest of the file", not the block. (b) Other negative spans (difference ≠ −1) raise `ValueError` from the io layer per block (executed) — the read fails, but by accident of buffered-IO semantics, not by any check in the wrapper; the session survives only because the UDPFS session loop catches handler exceptions (round 3 §1a). No span of any sign is ever compared against the block it is supposed to encode before the read.
- **Fix:** Validate the span where it is computed, as Go does: refuse `read_size < 0` or `read_size > block_size + slack` (a stored-raw block is exactly `block_size`; a compressed block larger than its own output plus framing is not a real CSO block) with the wrapper's own `ValueError`. One comparison at :124.
- **Justification (addition):** A file-controlled span currently decides an allocation size with no bound at all; the check is two comparisons against numbers the function already holds, and the correct bound is implemented in the sibling Go reader.
- **Benefit:** Per-block input becomes bounded by the block size; corrupt indexes fail at the block, with the wrapper's error, instead of slurping the file tail or dying inside `io`.
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ + EXECUTED)

## PS2SERVERS-066 / Both launcher block devices assign seek state before validating it — a failed seek leaves position, request end and (for raw devices) a stale cache armed for the next read
- **Category:** 6 (Bug — latent correctness)
- **Location(s):** `PS2-Servers/launcher/raw_storage.py:37-45` (`RawDevice.seek`: `_position` and `_request_end` assigned at :41-42, the capacity check raises at :43-44, the cache invalidation at :45 never runs); `PS2-Servers/launcher/virtual_exfat.py:228-233` (`VirtualExfat.seek`: both fields assigned at :229-230, the bounds check raises at :231-232); consequences in `virtual_exfat.py:267-325` (`read` clamps against the stale `_request_end`) and `raw_storage.py:47-80` (`read` trusts the retained cache by position range).
- **Problem:** EXECUTED at this pin, both halves. **RawDevice** (against a stub backend): after a valid seek + read primed the 64 KiB read-ahead cache, an over-capacity seek raised `OSError` — and left `_position = 51200`, `_request_end = 51,251,200` (device size 524,288) and the stale cache intact; a following `read(512)` then returned the **stale cached byte (0x07) with zero backend reads**, after the device content at that offset had changed to 0x09. **VirtualExfat** (on a temp folder): an out-of-range seek raised `OSError` and left `_position` beyond the disk end with `_request_end` also beyond `size` — disarming the only bounds check `read` applies — and a following `read(512)` returned 512 bytes (the gap-fill zero branch) from past the end of the virtual disk instead of failing. **Reachability, stated plainly:** through today's UDPBD server this cannot serve wrong data — every request seeks first and an `OSError` aborts that request before any read or write (`udpbd_server.py:205-262`, run loop :368-375). The defect is in the device classes' own contract (a failed seek must leave the device where it was), shared by both implementations of the interface, waiting for the first caller that reads after catching a seek error.
- **Fix:** In both `seek` methods, compute into locals and assign only after every check passes — and for `RawDevice`, clear the cache as part of the successful assignment. No new state, no new mechanism; each method shrinks by reordering.
- **Benefit:** A failed seek becomes side-effect-free in both devices; the stale-cache and disarmed-bounds states become unrepresentable.
- **Effort:** S. **Risk:** Low (successful seeks behave identically). **Confidence:** High (READ + EXECUTED); severity Low — latent, unreachable via the current server

## PS2SERVERS-067 / AES-CMAC's native backend is a probe-time-only fallback: a native failure mid-session raises out of the signing path and drops the connection instead of using the pure-Python reference in the same file
- **Category:** 6 (Bug — robustness)
- **Location(s):** `PS2-Servers/smb2_server/smb2_crypto.py:124-129` (`aes_cmac` dispatches to the probed native backend unconditionally; `aes_cmac_pure` is used only when the probe found nothing); probe/self-test at :173-186, :218-340; the raise surfaces at `PS2-Servers/smb2_server/smb2_server.py:492` (`smb2_crypto.signed(...)` while building a reply, outside `_dispatch`'s exception mapping) and lands in `_serve_client`'s `except OSError` (:403), which closes the connection.
- **Problem:** The module's own docstring presents the pure implementation as "the fallback and the reference"; at runtime it is only the reference and the probe-time fallback. If a native backend that passed its one-time self-test later fails on a real call (an EVP context failure under memory pressure is the plausible shape), every signed reply raises `OSError`, the connection thread logs a connection error and drops a Windows client mid-copy — for a computation the same file can do in pure Python at signature sizes (a CMAC over one message; the speed argument in the docstring is about throughput on game-copy READ replies, which is a degradation, not a reason to disconnect). Probability is low; the failure shape — total loss of the session instead of a slower signature — is the defect.
- **Fix:** In `aes_cmac`, catch `OSError` from the native call, drop the cached backend (`_NATIVE[0] = None`) and return `aes_cmac_pure(key, message)`. Three lines, using only what the file already has; subsequent calls go straight to the pure path instead of failing repeatedly.
- **Justification (addition):** Converts an executed-code-path session drop into a documented degradation, using the fallback the module already maintains and self-tests against.
- **Benefit:** A native-library hiccup can no longer kill signed SMB3 sessions.
- **Effort:** S. **Risk:** Low (behaviour changes only on a path that currently raises). **Confidence:** High (READ) for the mechanism; the mid-session native failure itself is INFERRED as possible, not observed
