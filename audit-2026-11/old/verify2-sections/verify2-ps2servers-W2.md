## Reasoning for non-VERIFIED items

### PS2SERVERS-026 — VERIFIED-DRIFT
The duplication mechanism survives intact and both halves are wired into the shipped GUI, so a user really does have two catalogues that can disagree: `game_library.Library` owns `achievement-catalog.sqlite3` (`launcher/game_library.py:63`) with its own `backup` (:178) and `import_catalog` (:195), and is what the "Manage game library…" window opens (`launcher/library_gui.py:11,20`, via `gui.py:641-648`); `library_catalog.Catalog` owns a different database, `catalog.sqlite3` (`launcher/library_catalog.py:106`), with its own backup/import (`:582-630`), and is what the Library tab's panel uses (`launcher/library_panel.py:11,201`, via `gui.py:1414-1416`); `library_index.py` (190 lines) is read by both (:290 and :453 respectively). The drift is the headline's UI count: "three library UIs" is not supported — there are exactly **two** UI implementations, `library_gui.py` (446 lines, `LibraryWindow`) and `library_panel.py` (561 lines, `LibraryPanel`). The third named component, `library_index.py`, is an index module with no UI. Corrected claim: two SQLite catalogues, two library UIs, one shared index module.

### PS2SERVERS-030 — VERIFIED-DRIFT
The mechanism is exactly as described: `launcher/serve.py:15-59` is a block of otherwise-unused stdlib imports whose comment states the purpose verbatim ("Explicitly import standard library modules required by dynamic server engines so PyInstaller, Nuitka, and static bundlers include them in frozen builds"), the re-exec dispatcher loads server modules by file path below it, and `tests/test_frozen_imports.py` exists precisely to guard the list ("serve.py works around that with a block of otherwise-unused `import` statements, and the list is maintained by hand"). The drift is the count in the title/problem: an AST count of the block gives **39** unconditional stdlib imports (lines 15-53, `argparse` … `zlib`) plus one platform-conditional import (`msvcrt` :56 / `fcntl` :58) — 40 effective per platform, not "45 modules". 45 is the block's line span (15-59), not its module count. Corrected citation: `launcher/serve.py:15-59` (45 lines, 39 + 1 conditional hint imports).

### PS2SERVERS-037 — WEAKENED
What survives: `_signature_of` (`http_server.py:398-434`) does stat every file in the scanned directories, `refresh()` (:530-543) rebuilds the index when the signature changes, and the check is invoked synchronously from request handling — the games.csv handler calls `index.games_csv()` (`:905-907`, `_serve_games_csv` :974), which calls `_refresh_if_stale()` (:756-759). What the finding omits narrows it materially. (1) The sweep is throttled: `RESCAN_INTERVAL = 5.0` (:274) and `_refresh_if_stale` (:742-754) returns immediately inside the interval — its own docstring states the per-request cost was already found and fixed: "Doing that per request made this server measurably SLOWER than the plain SimpleHTTPRequestHandler it is meant to beat, because the console issues thousands of 8 KB reads and every one of them paid for a directory walk." (2) The finding's "called from `games_csv`/`lookup`" is half-wrong: `lookup()` deliberately does **not** rescan ("Deliberately does NOT rescan. This is the hot path — one call per 8 KB of a game being streamed"), so per-read requests never pay it. (3) "Stats the whole game tree" overstates the default: `_scan_dirs` (:319-345) is flat (root + CD/DVD directories) unless the opt-in recursive mode is on, and recursive mode requires the path-aware profile (:280-289); the signature also reuses scandir's cached stat data, and I measured `_signature_of` at 0.8 ms over 300 files on local disk (full initial refresh 4.5 ms) — the network-drive magnitude remains INFERRED, as the finding itself flags. **Narrowed claim that survives:** at most once per 5 seconds, a games.csv (game-list) request — never a game-read request — synchronously stats every file in the scanned directories (flat by default; a bounded recursive walk only in opt-in recursive mode) and rebuilds the index in-request if anything changed.

### PS2SERVERS-038 — WEAKENED
The core is executed-proven, not just read: I copied `udpbd_server.py` alone into `/tmp/w2exec/alone/` (no `launcher/` package reachable) and ran it with `--virtual-exfat` — it dies at `udpbd_server.py:419` with `ModuleNotFoundError: No module named 'launcher'`; in-tree, the raw-device and virtual-exFAT modes import `launcher.raw_storage.open_raw_device` and `launcher.virtual_exfat.VirtualExfat` (:419-423), 427 + 325 = 752 lines of GUI-package code, and the fix direction (move them under `udpbd_server/`) is sound. But the finding's supporting premise — "Every other server directory is self-contained (SMB1/SMB2/UDPFS import only siblings/stdlib)" — is **false at this pin**, and quoting it is the defeating evidence: `http_server/http_server.py:47` has a top-level `from launcher import session_stats  # noqa: E402  shared by every server`; `smbserver_opl.py:1752` and `smb2_server.py:1789` import `launcher.session_stats.SessionStats` inside `main()`; `ps2servers_core.py:63` and `:587` import `launcher.release_metadata` and `launcher.session_stats`. The related claim that "`launcher/serve.py`'s path-loading has to make that import work" is also overstated — UDPBD inserts the repo root into `sys.path` itself (:417-420). **Narrowed claim that survives:** UDPBD is the only server whose *functional device implementations* (raw devices, virtual exFAT — 752 lines) live in the launcher package and are imported at runtime for its advanced modes; the other servers' launcher imports are small shared leaf utilities only (`session_stats` 131 lines, `release_metadata` 79 lines), mostly lazy — though HTTP's is top-level (see W2-CAND-1).
