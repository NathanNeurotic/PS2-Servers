## Full reasoning — non-VERIFIED verdicts

### PS2SERVERS-013 — WEAKENED (Python editions only; the Go edition refutes "every edition")

- **Claim as filed (pass 1):** no single-writer exclusion in UDPFS in *every edition*; locations include the Go server (`native/ps2servers-edge/internal/udpfs/server.go:334-338`) and the tree-wide statement that no `flock`/`O_EXCL`/`LockFile` equivalent exists in `udpfs_server/` **or** `native/ps2servers-edge/internal/udpfs/`.
- **What holds (re-derived):** the Python mechanism is exactly as described. Handles and write-assembly state are per-session (`udpfs_server/udpfs_server.py:3211-3219`, `Session` at `:3193ff`; sessions keyed by peer address, so a rebooted console on a new source port is a second session); files are opened with a plain `open(actual_resolved, py_mode)` at `:1923` and `:1928` with no lock, claim or exclusive flag; grep of `udpfs_server/*.py` finds no writer-reservation of any kind. Core (`udpfs_server/ps2servers_core.py:90`, `AutoUdpfsServer(UdpfsServer)`) overrides only transport/discovery methods (`__init__`, `run`, `_sendto`, `_get_or_create_session`, `_handle_data`, `_handle_discovery` and helpers) — no open/write handler — so the shipped Core path inherits the absence exactly. Two Python peers (or a stale + a fresh session) can therefore interleave writes to the same file, as claimed.
- **What is defeated:** the Go Edge edition **does** implement the exclusion, in substance if not by OS lock. `internal/udpfs/server.go:125-131` documents and declares the `writers` reservation map ("Two consoles writing the same file concurrently would interleave into corruption, so the second OPEN is refused with EBUSY"); `reserveWriter`/`releaseWriter` are at `server.go:134-176`; `openForWrite` (`internal/udpfs/operations.go:378ff`) calls it at `:427` and answers `-EBUSY` at `:431-435` when another peer holds the path. The repo carries the test the round-2 report cited: `TestSecondPeerCannotOpenTheSameFileForWriting` (`internal/udpfs/write_test.go:280-295`) — second writer gets `-eBUSY`, a concurrent reader is still allowed, close releases the claim (`:298-310`). The filed Go citation `server.go:334-338` is, in the pinned tree, a comment about per-peer goroutine ownership inside the session-close path — not evidence of absence. (Nuance that does **not** restore the claim for distinct peers: `openForWrite` permits a takeover via `st.TakeOverWriter(real)` when the holder is a replaced loader on the *same* endpoint — a documented handoff, not concurrent interleaving.)
- **Net:** the corruption class is real for the two Python editions (standalone + Core) and closed in Go Edge. Title/scope must drop "in every edition" — which is also how rounds 2–3 already treated it ("absence in the Python editions is round-1 PS2SERVERS-013"; "Go's reservation was re-read at this pin"). The fix direction in the finding (a per-canonical-path claim in the Python editions, copying the in-repo Go pattern) is unchanged.

- **What is defeated (executed):** the claim that this code "complete[s] a handshake and then lie[s] on every verb", including that "`h2_tree_connect` accepts any path without a share lookup":

So on the normal negotiate → session-setup → **tree-connect** sequence a real client gets a dropped connection, not a fake success; the bypass above works only because `serve_conn` dispatches commands in any order and a client can skip TREE_CONNECT.

- **Net:** the finding's core — a third, fake SMB2 implementation inside the SMB1 file, a credential-gate bypass, silent data discard on WRITE, no directory listing — stands. Its "answers success on every verb" framing does not: TREE_CONNECT and CLOSE are arity-broken and crash the thread instead. The two arity defects are filed separately as PS2SERVERS-114 (they also occur on *well-formed* requests, which -044 does not cover). ## New defect candidates

### PS2SERVERS-114 / SMB1 server's embedded SMB2: TREE_CONNECT and CLOSE always raise `struct.error` and kill the connection thread — on well-formed requests

- **Category:** 6 (Bug / robustness)
- **Location(s):** `PS2-Servers/smbv1_server/smbserver_opl.py:572-581` (`h2_tree_connect`: `struct.pack("<BBII", …)` given 5 values for 4 format items), `:612-614` (`h2_close`: `struct.pack("<HHQQQQQI", …)` given 9 values for 8 format items); uncaught because the SMB2 branch of `serve_conn` (`:1435ff`) runs under the same `except (ConnectionError, OSError)` at `:1497` that PS2SERVERS-044 covers for SMB1.
- **Problem:** EXECUTED at this pin: both handlers raise `struct.error` on every call, regardless of input. Driven through `serve_conn`, one well-formed SMB2 TREE_CONNECT (0x0003) — the third message of every normal SMB2 session — terminates the connection thread with a traceback, and CLOSE (0x0006) does the same. This is distinct from PS2SERVERS-044 (there, *truncated SMB1* requests raise in the handler); here the requests are well-formed and the defect is in the handlers' own reply construction, so no client behaviour can avoid it. It also means the fake SMB2 of PS2SERVERS-042 cannot complete the standard session sequence at all.
- **Fix:** Correct the two pack formats to match the reply layouts they intend (add the missing `I` to `"<BBII"` → 5 fields; drop the surplus value or add the missing field in `h2_close`), or — preferably, as PS2SERVERS-042 already recommends deleting this whole implementation — delete it. If any of it is kept, `struct.error` should be caught alongside `OSError` in `serve_conn` (the PS2SERVERS-044 fix) so a handler bug drops one reply, not the thread.
- **Benefit:** A guaranteed thread-kill on a normal protocol message removed; no lines saved if fixed in place (deletion under -042 removes ~130 lines including this).
- **Effort:** S. **Risk:** Low. **Confidence:** High (READ + EXECUTED, both directly and through `serve_conn`)

### PS2SERVERS-115 / SMB1 server's embedded SMB2: the SMB2 header packer/parser is 66 bytes, not 64 — `Command` is encoded as a 4-byte field

- **Category:** 6 (Bug / protocol correctness)
- **Location(s):** `PS2-Servers/smbv1_server/smbserver_opl.py:511-527` (`pack_smb2_hdr`, format `"<4sHHIIHIIQQQ16s"`, `struct.calcsize` = **66**) and `:529-535` (`Smb2Req`, same format); the header's own StructureSize field is written as 64.
- **Problem:** EXECUTED at this pin: in the pack format, `Command` is the second `I` (4 bytes) where MS-SMB2 defines Command as 2 bytes followed by CreditRequest/Response (2 bytes); every field after Command (credits, flags, message id, session id) is therefore shifted 2 bytes, and the produced "header" is 66 bytes that declare StructureSize 64. The implementation's own parser uses the identical wrong format, so in-repo loopback exchanges parse consistently and no in-repo test notices; but `Smb2Req` outright rejects a correctly-sized 64-byte SMB2 header (`struct.error: unpack_from requires a buffer of at least 66 bytes…`, observed when a 64-byte frame was fed to it during this verification), and a spec-conformant client's header parse of these replies would misread every field after Command (INFERRED for real-client interop; the 66-vs-64 size and the parser rejection are executed). This is a second, independent reason the PS2SERVERS-042 implementation cannot talk to a real SMB2 client, beyond its dummy handlers.
- **Fix:** None in place — this is further support for PS2SERVERS-042's deletion. If the implementation were ever kept, the format would need `Command`/`Credits` as `"<HH"` and the Reserved/TreeId split restored to reach a true 64-byte header, with a wire-size assertion (`calcsize == 64`) in a test.
- **Benefit:** Records why "just fix the dummy handlers" would still not make this implementation interoperable; prevents a partial fix of -042 from being mistaken for a working SMB2.
